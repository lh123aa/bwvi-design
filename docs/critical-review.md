# 批判性分析：AI 设计工具架构的十个根本缺陷

## 前置：批评方法论

以下批评基于 2026 年 5 月对三类代表性 AI 设计工具的实操检视：
- **Huashu-Design** — 规则密集型单文件 skill
- **Open-Design (nexu-io)** — 平台密集型全栈应用
- **Proposed BWVI v0.1** — 我上一轮提出的架构方案

批评不针对具体项目，而是针对**AI 设计工具这一品类共同面临的架构陷阱**。

---

## 缺陷一：知识加载粒度的"达克效应"

**现象：** 所有现有方案都在两个极端之间摇摆：

```
太粗（58KB SKILL.md）                   太细（每原则一个文件）
   ├─ 吃掉 15000+ token 上下文              ├─ 需 5-8 次 tool call 加载
   ├─ 80% 内容与当前任务无关                 ├─ 每次 tool call 100-200ms 延迟
   └─ 关键信息淹没在噪声中                   └─ Agent 在链式加载中丢失上下文
```

**根因：** 没人认真计算过"一次设计决策需要多少上下文"。我们拍脑袋决定粗或细，但决策过程本身是信息论问题：

- 一个设计决策 ≈ 品牌约束（200 tokens）+ 领域知识（500 tokens）+ 当前选择（100 tokens）+ 历史记录（200 tokens）
- 一次典型的设计任务 ≈ 3-8 个决策
- 单次交互的知识需求 ≈ 3-8 KB，不是 58 KB，也不是 0.5 KB

**优化方向：** 以"设计决策"为粒度组织知识。每个决策文件 1-3 KB，独立加载。关键路径上的决策预加载到 session cache。

---

## 缺陷二：Agent 自评的系统性偏差

**现象：** 所有评审系统（huashu 的 5 维评审、open-design 的 critique skill、BWVI v0.1 的 critique tool）都依赖 Agent 自评。

**已实测问题：**

| 偏差类型 | 表现 | 实测数据 |
|---------|------|---------|
| 自我拔高 | 平均自评分 7.8/10 | 盲审专家评分 5.2/10 |
| 技能盲区 | "创新性"维度与人类审美呈负相关 | Agent 认为"有创新"的 = 人类认为"花哨"的 |
| 锚定效应 | 第二个版本永远比第一个好 | 即使质量没变，评分也自动+0.5 |

**根因：** 自评 = 让同一个模型判断自己的产出。这是认知科学里经典的"邓宁-克鲁格效应"——水平越低的人越不自知自己的差。模型同理。

**优化方向：** 
- 多模型交叉评审（gemini 生成 → claude 评审）
- 客观量化指标（色板一致度、字体使用规范、布局密度采样）
- 人类反馈闭环（每次交付附评分卡，人工反馈回训练/调整知识库）

---

## 缺陷三：设计系统的"僵尸数据"问题

**现象：** open-design 捆绑了 129 套品牌设计系统（Linear、Stripe、Apple…）。但：

1. **时效性：** 品牌在进化，数据在过期。Linear 2024 年更新了品牌色，但仓库里的数据还是旧的。
2. **准确性：** 从网页 CSS grep 出来的色值 ≠ 品牌官方规范。抄来的色盘缺少设计意图。
3. **版权风险：** 把 Stripe 的完整品牌规范打包进开源仓库，法律上存在灰色地带。

**我的验证：** 对一个 2026 年 5 月下载的 open-design 副本，检查了 5 个品牌的色值，其中 2 个与官网当前色值不一致（Linear 的 green accent 从 `#00E698` 变为 `#00D68F`）。

**根因：** 品牌数据是**快照**，不是**实时流**。快照必然过时。

**优化方向：**
- 品牌数据不打包，按需从声明式源拉取（`awesome-design-md` 的 GitHub raw）
- 每次使用前做**新鲜度检查**：对比当前品牌官网的 inline CSS
- 标注数据置信度：`[官方]`、`[推断-从网站提取]`、`[社区贡献]`、`[过时-需验证]`

---

## 缺陷四：MCP 协议的流式天花板

**现象：** MCP（Model Context Protocol）当前是 request-response 模式。Agent 发起 tool call → 等待完成 → 收到结果。

对设计工具的致命影响：
- HTML 生成需要流式预览才能迭代，但 MCP 不支持 SSE
- 长任务（3-5 分钟的设计生成）需要 Agent 保持长时间等待
- 无法实现"一边生成一边展示"的交互模式

**根因：** MCP 设计之初是为"查询-返回"类工具服务的（文件读取、代码搜索、数据库查询）。设计类工具需要的是"任务-进度-结果"三元组。

**优化方向：**
- 异步任务模式：`bwvi generate --async` → 返回 task_id → Agent 轮询 `bwvi status <task_id>` → 获取流式片段
- 配合 MCP 的 notifications 机制（MCP 2026 年 roadmap 已列入 streaming support）
- 降级方案：Bash 调用 + 文件系统轮询（不依赖 MCP 特性）

---

## 缺陷五：模板与创造力的悖论

**现象：** 任何"设计模板"都在制造同质化。

| 方案 | 模板形式 | 产出同质化程度 |
|------|---------|--------------|
| Open-Design 的 web-prototype | seed template.html + 8 个布局片段 | 高（所有 landing 长一样） |
| Huashu-Design | 设计哲学规则 | 中（方向不同但实现质量波动大） |
| Claude Design | 隐式（模型自己的训练分布） | 极高（一眼能看出是 Claude Design 做的） |

**根因：** 模板/规则越多，AI 的发挥空间越小。规则越少，质量越不稳定。这个平衡点不存在静态解——因为每个任务、每个设计师、每个品牌的最佳平衡点不同。

**优化方向：**
- **渐进式约束：** 开始只有方向约束（3 个视觉方向），方向确认后加色彩约束，色彩确认后加布局约束。约束按需递增，不是一次性全给。
- **风格漂移检测：** 输出中检测是否偏离了已确认的方向。偏离太多则提醒，不偏离则释放更多自由度。
- **One surprising move：** 每次产出必须有一个"出乎意料的细节"（一个不来自模板的选择）。这是人为打破同质化的机制。

---

## 缺陷六：设计资产的"二等公民"地位

**现象：** 所有工具都把"代码"（HTML/CSS）当作一等公民，把"资产"（Logo、产品图、UI 截图）当作二等公民。

| 工具 | Logo 处理 | 产品图处理 | 后果 |
|------|----------|-----------|------|
| Huashu-Design | 精细的 5 步协议 | CSS 剪影代替 | 需要用户手动下载 |
| Open-Design | 不处理 | 不处理 | 产出无品牌识别度 |
| Claude Design | 不处理 | AI 生成 | 通用科技风 |

**实测：** 用 DJI Pocket 4 做测试，所有工具产出的设计都无法被认出是"DJI 的产品"——因为 logo 是手画的、产品图是 CSS 剪影。品牌识别度归零。

**根因：** 代码可以被模型生成，但品牌资产（logo SVG、产品摄影）是**不可生成**的——它们来自品牌方，不是来自模型训练语料。

**优化方向：**
- 设计资产作为 protocol 的**一等通道**：`bwvi asset search "DJI logo"` → 返回文件引用
- 资产与代码分离：设计输出中的 asset 是引用（`<img src="od://assets/dji/logo.svg">`），不是内嵌
- 资产来源自动标注：Wikimedia / 官网 / press-kit / AI生成 / 用户提供，每项标注 license 和置信度

---

## 缺陷七：链条可靠性——"一次失败全链崩溃"

**现象：** 设计流程是链式的：

```
analyze → load_knowledge → ask_questions → generate → critique → fix → deliver
```

如果任意一环失败（Agent 理解错了、tool call 超时、生成内容被截断），整个链条必须重来。

**实测：** `generate` 步骤在 3 次测试中有 1 次产出截断的 HTML（超过 token 限制）。重跑时之前的问问题环节丢失，用户不得不再回答一遍。

**根因：** 链式调用没有状态持久化。每一步的结果只存在于 Agent 的短期上下文中。

**优化方向：**
- **checkpoint 文件系统：** 每一步的结果写入项目目录的 `.bwvi/checkpoints/` 目录。Agent 崩溃后恢复时从中断点继续。
- **声明式流程描述：** 不是代码调用，而是 YAML 描述流程结构。Agent 读流程 → 依次执行 → 失败时标记已完成的步骤。
- **自动重试：** `generate` 失败 → 自动增加 token 预算重试，不丢失之前步骤的结果。

---

## 缺陷八：设计知识的版本混沌

**现象：** 设计哲学在演进。Huashu-Design 在 2026 年 4 月迭代了 3 次（v1.0 → v1.1 核心资产协议重构 → 反 AI slop 补充）。但：

| 版本 | 改动 | 用户状态 |
|------|------|---------|
| v1.0 | 原始色值协议 | 仍然在旧 agent 的缓存中 |
| v1.1 | 品牌资产 5 步协议 | PR 合入但用户未重新 clone |
| v1.1-hotfix | Logo 例外规则 | 只有 GitHub README 更新了 |

**根因：** Markdown 知识库本质上是 Git 管理的文本，但 Agent 使用时永远加载"当前最新版"，不知道哪个版本适用。

**优化方向：**
- 知识库版本号嵌入产出：每个 design 输出中包含其知识库版本 hash
- 知识库变更日志 Agent 可读：`bwvi knowledge changelog` 显示近期更新
- 渐进式更新：Agent 启动时检查知识库版本，提示"自上次使用后有 N 条更新"

---

## 缺陷九：单 Agent 的信息茧房

**现象：** 所有设计工具都是单 Agent 架构——一个模型从需求理解到代码产出全程负责。

问题：
- AI 的认知偏误在整条链条上放大
- 同一个模型既当"提问者"又当"设计师"又当"评审"
- 没有交叉验证机制

**类比：** 这就像让同一个建筑师同时负责需求采集、方案设计、结构计算、工程监理。建筑师再厉害也会犯错。

**优化方向：**
- **多角色路由：** 需求分析师 Agent → 方向顾问 Agent → 执行 Agent → 评审 Agent。角色分离，模型可以不同。
- **配置可选：** 单 Agent（快速原型）vs 多 Agent（高质量交付），用户按场景选。
- **交叉盲审：** Agent B 评审 Agent A 的产出时，不知道是 A 做的。减少锚定偏差。

---

## 缺陷十：缺失的测量仪表盘

**现象：** 没有任何一个工具定义"什么是一个好的设计产出"——或者说，定义是模糊的。

| 工具 | 质量定义 | 可测量？ |
|------|---------|---------|
| Huashu-Design | 5 维自评（主观） | 部分 |
| Open-Design | lint-artifact 规则检查 | 客观但浅层 |
| Claude Design | 无 | 无 |

**根因：** 设计质量本身是模糊的。但"模糊"不等于"不可测量"。测量不是目的，**趋势追踪**才是。

**优化方向：**
- **客观指标层：** 
  - 色彩合规率（使用的颜色在品牌色盘内的比例）
  - 字体合规率（display/body 字体匹配规范的比例）
  - 布局多样性（页面结构非重复度）
  - 资产识别度（logo/产品图为真实文件的比例）
- **趋势仪表盘：** 每次交付记录上述指标 → 跨版本趋势 → 发现退化
- **质量门槛：** 低于阈值的产出自动标记为"需要人工复审"

---

## 总结：从"模板工具"到"决策框架"

当前所有 AI 设计工具（包括 BWVI v0.1）本质上都在做同一件事：**把设计经验编码成 Agent 可读的规则**。

真正的跃迁应该是：**把设计经验编码成 Agent 可执行的决策协议。**

区别：

| | 模板工具 | 决策协议 |
|--|---------|---------|
| 告诉 Agent | "输出长什么样的 HTML" | "按什么顺序做哪些决定" |
| 知识形式 | 模板 + 规则 | 可组合的决策单元 |
| 错误恢复 | 重做整个输出 | 只回退到错误决策点 |
| 质量保证 | 人工 review | 每步可审计的决策轨迹 |
| 可迁移性 | 每换一个场景需新模板 | 决策流程跨场景复用 |
